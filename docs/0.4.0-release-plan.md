# GDDraw 0.4.0 Release Plan

## Goal and status

**Theme: smoother 3D painting and more precise 2D drawing.**

Build on 0.3.0's layers and hierarchy painting with continuous cross-object
brush gestures, reusable right-side panels, color palettes, and gradients.
This is an implementation plan, not a statement that the features have shipped.
The released 0.3.0 behavior is the regression baseline.

**Scope decision — 2026-09-27:** Feature additions for 0.4.0 are complete.
Exact selection sizing is deferred to a later revision, with no release assigned.
It is not a 0.4.0 release requirement. Remaining work is release validation,
documentation, and packaging.

Documentation checkpoint: the README, offline manual, navigation manifest, and
What's New now describe the completed 0.4.0 scope. Existing release history is
preserved. The documentation browser suite passes 67 assertions, and all 66
relative links checked across the packaged manual and README resolve. Runtime
version declarations and publishing are separate release steps.

## 1. Continuous cross-object painting

### User behavior

- One held brush or eraser gesture can cross imported objects and material
  bindings, including independent textures and objects sharing one texture.
- One gesture creates exactly one undoable action. Undo restores every affected
  texture; Redo reapplies the entire gesture.
- Returning to an object during the same gesture preserves its earlier edits.
- Target Lock continues to reject other paint targets. Different bindings of
  the same shared texture remain compatible with that target lock.
- Locked paint layers or ancestors cannot receive pixels. Passing over a locked
  or unsupported object does not end the gesture or draw through that object.
- Shapes remain restricted to their existing compatible surface rules. Fill
  and eyedropper remain single-click operations.

This feature makes the input gesture continuous. It does not promise automatic
UV seam repair, padding, matching world-space brush sizes across different
texel densities, or painting objects that were not imported.

### Implementation contract

1. Resolve each hit by preview object, material binding, paint target, and UV.
2. Finish the current texture segment when crossing a binding or target boundary,
   without ending the pointer gesture or committing its overall history action.
3. Switch the editable canvas and selected layer to the destination target,
   reusing prepared previews, caches, and layer state.
4. Begin the next segment at that hit's own UV coordinate. Never interpolate
   from the previous object's UV coordinate or across a missed/blocked hit.
5. Respect each target's dimensions and remembered selected paint layer. Retain
   the existing texture-pixel brush-size convention for mixed-resolution targets.
6. Keep all affected live previews updated, including shared-texture bindings.
7. Capture an immutable pre-gesture history state once and finalize one action
   after release. Preserve the state needed to restore every changed target.
   Use the existing session history contract before considering optimizations.
8. Keep routing state separate from visible selection synchronization. Do not
   rebuild the Layers tree or repeatedly change Godot scene selection mid-drag.
   On release, synchronize the final accepted paint destination once.
9. A no-op gesture creates no history entry. Cancellation restores all touched
   targets together and creates no entry. Focus loss, source removal, Stop
   Editing, and document transitions must resolve the gesture through one
   explicit commit/cancel path before replacing state.

Likely integration points: `gddraw_dock.gd`, `gddraw_canvas.gd`,
`gddraw_3d_layer_coordinator.gd`, `gddraw_layer_session.gd`, and
`gddraw_history.gd`. Keep gesture transaction logic separate from individual
texture-segment logic; do not create one history entry per object.

### Acceptance gates

- Independent objects, separate slots on one mesh, shared atlases, and
  mixed-resolution textures all support a single gesture.
- A → B → A strokes preserve both visits and undo/redo as one action.
- Locked layers, locked groups, Target Lock, UV discontinuities, occlusion,
  unsupported surfaces, and pointer misses preserve existing protections.
- Cancellation and interrupted gestures restore coherent pixels, dirty state,
  selected layers, and active target routing.
- No Layers tree rebuild or scene-selection churn occurs per drag sample.
- Measure large-texture strokes and history memory against the 0.3.0 baseline;
  verify native editor responsiveness as well as headless pixel correctness.

## 2. Reusable right-side dock

### User behavior

- Keep the Layers icon in the right-side rail and add a Palettes icon below it.
- Each rail icon independently toggles its panel open/closed. Every open panel
  stays highlighted, including inactive tabs. Reopening restores tab/split placement.
- Support panels as tabs in a shared group, side by side in a horizontal split,
  or above/below one another in a vertical split.
- Allow moving a tab between groups and resizing splits with visible handles.
- Keep this arrangement available in 2D, 3D, and both canvas split layouts.
- Persist panel placement, active tabs, visibility, and split ratios per project.
  Dock layout changes must not dirty artwork or enter drawing history.
- Provide a reset-layout action and sensible minimum sizes. Narrow docks must
  remain usable without losing access to icons or trapping a hidden panel.
- When tabs overflow, show compact left/right buttons that select adjacent
  tabs and keep the active tab visible. Disable the corresponding boundary
  arrow, hide both when everything fits, and provide tooltips, keyboard access,
  and usable click targets.

### Architecture and bounds

Introduce a dedicated panel host with stable panel IDs and registration of
title, icon, content control, and minimum size. Layers and Palettes become its
first clients. Future GDDraw panels should register without adding bespoke
layout branches throughout `gddraw_dock.gd`.

The reusable-dock milestone stops with Layers as its only production client.
Temporary test panels exercise multiple tabs and splits. Palettes and its rail
icon follow in the palette milestone; no placeholder palette feature is needed.

Use Godot containers for tab groups and horizontal/vertical splits. Separate
panel lifetime from placement so moving a panel does not recreate its model,
lose selection, reconnect signals repeatedly, or duplicate history ownership.
Store a versioned, validated layout description; unknown panel IDs and invalid
ratios fall back safely. Migrate existing Layers width/expanded preferences.

This is docking inside GDDraw's right-side workspace. Floating OS windows,
cross-editor docking, and a public third-party extension API are outside 0.4.0.
The goal is to make later built-in panels easy to add.

### Acceptance gates

- Layers and Palettes work tabbed, side by side, and top/bottom.
- Moving, hiding, reopening, and restoring panels preserves their state.
- Layout survives an editor restart and handles missing or malformed settings.
- All four workspace layouts work at narrow and short sizes, including keyboard
  focus, shortcuts, tooltips, drag feedback, and resize limits.
- Collapsing the last panel leaves the rail accessible; resetting layout recovers
  a usable default. No panel operation modifies artwork or drawing history.

## 3. Palette import and viewing

### Initial scope

- Open Palettes from the new icon below Layers in the right-side rail.
- Import named palettes, display swatches, and switch between imported palettes.
- Select a swatch to set the foreground color; provide an explicit secondary
  action for assigning the background color, with a clear tooltip.
- Show color values on hover and indicate selected colors without relying only
  on color differences. Support keyboard selection.
- Palette choices feed the existing foreground/background controls used by 2D
  drawing, 3D painting, text, fills, and gradients.
- Preserve imported palettes and the selected palette across editor restarts
  using project-scoped storage outside the replaceable plugin directory.
- Import failure leaves the current palette intact and explains the problem.

Implemented first formats: GIMP `.gpl` and UTF-8 `.hex`/`.txt`, with exact
syntax and failure behavior documented in the milestone-3 checkpoint and
[offline palette manual](../addons/GDDraw/docs/palettes.md). Parsed colors and
names live in project storage so the external source need not remain available.

Palette authoring was subsequently approved as the extension documented below.
Image-based palette extraction, online services, and proprietary formats remain
deferred.

### Acceptance gates

- Valid imports preserve swatch order and supported metadata.
- Invalid/truncated inputs cannot replace or corrupt a usable palette.
- Foreground/background changes stay synchronized with existing controls and
  do not modify canvas pixels or create undo entries by themselves.
- Palettes remain accessible after dock rearrangement and editor restart.
- Updating GDDraw does not overwrite project palettes.

## 4. Gradient tool

### User behavior

- Add Gradient to the left drawing toolbar alongside brush, eraser, and fill.
- Support linear and radial gradients using foreground/background colors.
- Click-drag to position the gradient and preview it before release commits one
  undoable edit. Escape cancels without changing pixels or history.
- Apply only to the active paint layer, respecting selections, effective layer
  locks, alpha lock, and the document bounds.
- Provide reverse-direction control and consistent endpoint/alpha behavior.
- Palette swatches can supply either endpoint through the existing color controls.

The initial tool operates in the 2D canvas, including the texture canvas of a
3D session; its result updates the 3D preview. Direct gradient dragging across
3D surfaces, multi-stop editors, gradient presets, and editable gradient layers
are deferred.

Define interpolation and compositing explicitly, especially transparent
endpoints, selection edges, zero-length drags, and partial-opacity layers.
Reuse the existing draft/commit lifecycle; avoid adding complete-session history
snapshots for every preview update. Choose a shortcut only after auditing current
bindings and update tool menus, options, cursors, and documentation together.

### Acceptance gates

- Deterministic pixels for linear/radial gradients, reversed endpoints, alpha,
  degenerate drags, selections, and alpha lock.
- Preview matches committed output and cancellation restores the previous image.
- One gesture is one undo action; locked/no-op operations add no history entry.
- Visible composites and 3D previews update correctly with multiple layers.
- Large-canvas preview remains responsive in the native editor.

## Deferred: exact selection sizing

Retain this improvement for a later revision: expose width and height in
pixels for a floating pixel selection, with a linked aspect-ratio option.
Use the existing transform pipeline and sampling behavior. Editing one field
with the link enabled adjusts the other using a documented rounding rule.

This resizes selected pixels, not the document, a Scene object, or an entire
layer stack. Numeric edits should preview and commit as one logical transform,
respect locks and selection bounds, and support cancellation and undo/redo.
Decide and document the fixed resize anchor before implementation.

## Implementation order

1. Capture focused regression and performance baselines on the 0.4.0 branch.
   Verify the current architecture against this plan before editing.
2. Implement and validate cross-object gesture transactions first, since they
   carry the highest correctness risk.
3. Extract the right-side panel host with Layers as its only client; verify that
   the existing workflow survives before introducing a second panel.
4. Complete split/tab layouts and persistence with temporary test clients, then
   add the production Palettes panel in the next milestone.
5. Add gradients using the existing color controls and draft/history lifecycle.
6. Complete native editor checks, documentation, compatibility checks, and
   packaging validation. Freeze feature scope before the release candidate.

Each phase should leave a usable plugin and a reviewable change. Do not combine
unrelated history, panel-host, and raster changes into one untestable rewrite.

## Release verification and packaging

- Run focused tests after each feature, then the full regression suite on the
  final candidate. Verify Godot 4.4 compatibility and Godot 4.7 native behavior.
- Run suites with shared fixture paths sequentially, not concurrently.
- Manually test actual multi-object scenes, mixed texture resolutions, dock
  layouts, palette imports, gradient previews, existing selection transforms, and save/reopen.
- Preserve 0.3.0 layered-project compatibility unless a separately justified
  format change includes backward-loading coverage.
- Update tool documentation, shortcuts, and `docs/whats-new.md` with 0.4.0 first.
- Set both plugin version declarations to 0.4.0 during release preparation.
- Package `GDDraw-v0.4.0.zip` with `addons/GDDraw/` at the archive root. Exclude
  `.import`, `.godot`, local tests, user assets, and other generated content.
- Validate the actual ZIP with the released 0.3.0 updater before publishing.
  The 0.3.0 release initially failed because generated `.import` files were
  included; archive inspection is a release gate, not an optional cleanup.
- Test the real 0.3.0 → 0.4.0 update/restart path and verify What's New appears
  once, then remains accessible through Help without reopening on every launch.

## Deferred features

Material-channel painting, a complete brush engine/editor, animation editing,
sprite-sheet assembly, triangle-fill tools, additional shapes, history browsing,
editable layer effects, smudge, and UV seam padding remain future candidates.
Do not expand 0.4.0 to include these without revisiting the release scope.

### Performance assessment

Representative headless measurements in milliseconds, two independent targets,
one visible Base layer each, one-pixel brush, overlap enabled:

| Engine / target size | Start | Cross | Return | Release | Undo | Redo |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 4.7 / 2048² | 1.7 | 1.8 | 1.9 | 72.1 | 186.5 | 185.1 |
| 4.7 / 4096² | 6.1 | 6.2 | 6.2 | 277.5 | 746.5 | 732.3 |
| 4.4 / 2048² | 1.7 | 1.8 | 1.8 | 83.9 | 216.6 | 214.1 |
| 4.4 / 4096² | 6.1 | 6.2 | 6.2 | 325.9 | 852.4 | 837.1 |

With overlap disabled at 4096², initial start/cross were 11.8/11.8 ms on 4.7 and
11.4/12.0 ms on 4.4; return remained 6.4/6.7 ms. The initial coverage allocation
is retained across revisits. Each full-resolution Float32 coverage array can
consume another 64 MiB per 4K target until release.

For comparison, the unchanged 0.3.0-behavior layer benchmark measured 4096² tiled
refresh at 15.5/15.7 ms and cached target switching at 2.2/2.2 ms before edits
(4.7/4.4). Post-change runs measured 18.8/19.8 ms and 4.5/2.2 ms respectively.
These are individual noisy measurements of constituent operations, not an
equivalent pre-existing cross-object gesture: the baseline did not support one.
Full partial-opacity 4K compositing remains roughly 0.9–1.1 seconds in these
benchmarks; tiled live updates avoid doing that full operation per sample.

Two 4K targets retain **128 MiB of editable-image history pixels** for one
snapshot, the same complete-session history scope used by the baseline. This
excludes immutable eraser/saved baselines, live/composited images, coverage,
temporary comparisons, and GPU resources. Sharing bindings adds no duplicate
paint-target snapshot. No history-format or delta-history redesign was made.
Release and undo/redo still scan/restore substantial image data and can hitch;
these timings and calculated payload sizes do not measure editor RAM/VRAM,
real GPU uploads, or responsiveness while processing dense pointer events.

### Exact formats, storage, and failures

- Inputs must be valid UTF-8 and at most **1 MiB / 1,048,576 bytes** before
  reading/parsing. Optional BOM, surrounding whitespace, LF/CRLF, and blank
  lines are accepted. Maximum **4,096 swatches** per palette. Empty palettes,
  oversized files, excessive counts, and malformed records reject the complete
  candidate without replacing existing memory or storage; errors give line
  numbers where applicable. No silent truncation or format inference.
- `.hex`/`.txt`: exactly one `#RRGGBB` or `#RRGGBBAA` token per color line,
  case-insensitive digits. Full-line `;` and `//` comments are allowed; `#` is
  part of a color. Inline comments, extra tokens, and shorthand are rejected.
  Filename stem supplies the name; alpha, duplicates, and order are preserved.
- `.gpl`: verified against the [official GIMP specification](https://developer.gimp.org/core/standards/gpl/).
  Requires `GIMP Palette` first. Optional nonempty `Name:` and integer
  `Columns:` (0–255) each occur at most once before colors. Columns is validated
  but the responsive UI chooses its own layout. Full-line `#` comments and RGB
  channels 0–255 with optional swatch names are accepted; colors are opaque.
  Decimal leading zeros and explicit positive signs are accepted. Whitespace-only
  lines, indented comments, surrounding whitespace, and Columns without Name
  are documented tolerance beyond the strict specification. Metadata after
  colors or repeated metadata is rejected.
- Normalized version-1 JSON lives at
  **`res://gddraw/palettes/collection.json`** via `GDDrawStoragePaths`. Its fields
  are `version`, `next_id`, `active_id`, and ordered `palettes`; each palette has
  `id`, `name`, and ordered `swatches` with eight-digit RGBA `color` and `name`.
  IDs increase without reuse. Same-name imports use deterministic `(2)`, `(3)`
  display suffixes and never overwrite a palette. Import selects the new view
  without changing drawing colors. Source files may disappear afterward.
- Collection validation bounds normalized JSON to **64 MiB / 256 palettes**,
  checks stored swatches and counters, and rejects missing/duplicate IDs,
  malformed records, and unsupported versions. Invalid data is preserved and
  writes are blocked with a repair/reopen message. Missing storage is empty;
  a missing active ID safely selects the first palette and reports a warning.
  Loading/migration never creates directories or rewrites the collection.
- Writes validate the entire candidate, check for stale external edits, flush
  and verify a unique sibling temporary file, and perform one replacement
  rename. The old destination is never deleted first. Failed writes or rename
  leave the old collection and in-memory selection unchanged; temporary cleanup
  is attempted. Memory and signals advance only after success. Collection data
  is separate from layout metadata and artwork serialization, outside plugin
  updates. Concurrent multi-process editing is not a supported workflow.
- Added the offline palette page and navigation entry, interface/storage/key
  references, and architecture contract. Existing Lucide notices already cover
  the supplied palette assets. Authoring, extraction, online services, other
  formats, and deferred release features remain outside this milestone.
